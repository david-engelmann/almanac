## 2. Perfection pass, the counter case read firsthand

The strongest counter case against this product, stated plainly.
Generation is a commodity. A browser form can produce a valid ard.json
in five minutes, Lighthouse already audits the file, and platform
vendors will bundle generators with their own server tooling within a
year. A repo whose value is generation will be worth nothing by the
time it is good. This seat accepts that case in full.

Prior art read firsthand for this record, beyond the dossier.

- Lighthouse. The ARD audit checks presence and schema at a moment in
  time. Release 13.6.0 of 2026-10-27 moved its gatherer to try ard.json
  before ai-catalog.json and warns on the legacy path. It never opens
  the MCP server the catalog announces and never compares the
  announced tools with the served tools. It is a snapshot, not a gate.
- Browser generators. The Netsurge generator, ARD Catalog Lab and the
  Cubbbix suite produce a file once, in a browser, from form fields a
  person typed. No repository, no CI, no memory of what the server
  served yesterday. The dossier established this and the seat found
  nothing newer.
- ardregistry.net. This registry crawls the ecosystem and measured 527
  publishers on 2026-11-20, with 52 percent still stranded on the
  superseded ai-catalog.json path. It measures publishers. It does not
  maintain any one publisher's catalog and it offers no CI gate.
- The MCP server card extension, SEP-2127, final on 2026-10-06. This
  is the finding that sharpens the dual path contract. The MCP
  extension's discovery notes still tell clients to read
  ai-catalog.json and do not mention ARD. So the legacy path is not
  merely ARD history. Two live reader populations sit on opposite
  sides of the rename, ARD registries on ard.json and MCP card readers
  on ai-catalog.json. Serving only one path strands the publisher from
  the other population today, not in a deprecated past.
- GitHub Agent Finder and the ARD working group give the standard its
  distribution. The standard is backed by GitHub, Google, Microsoft
  and Hugging Face, and ARD was submitted to the IETF on 2026-10-30 as
  three Internet Drafts. Building against ARD rather than a private
  format is the right bet. Building a registry is not this seat's job.

Sharpest form, restated after the counter case. The drift check is
the product and generation is its onboarding. A publisher runs
almanac once to generate a catalog from real artifacts, and that
run also records a baseline of what the server actually served.
Every later run compares the published catalog, the baseline and the
live surface, and fails when they diverge. The generator exists so
the baseline exists. If generation were the whole product, this seat
would recommend killing it.

What remains true if the counter case lands in full. Suppose every
platform ships a free generator inside its own server tooling within
a year. Four things survive that. One, platform generators write for
their own surface and their own registry. None of them maintains the
other path of the dual path pair, and none of them writes the
catalog a rival platform's readers consume. Two, a generator bundled
with a platform has no reason to fail that platform's own customers
in CI, and every reason to stay a friendly snapshot tool like
Lighthouse. The gate's willingness to go red is the product, and it
is the part a platform will not ship against itself. Three, the
baseline is publisher property. It records what the server served at
generation time, it lives in the publisher's repo, and it is the
evidence every later check stands on. A platform tool that generates
and forgets leaves the publisher with nothing to check against.
Four, the stranded majority is not on any one platform's tooling
roadmap, because the stranded publishers are by definition the ones
the platforms have not reached. Serving them is unclaimed work.
If all four somehow fall, what is left is a small honest tool that
kept a handful of catalogs true, and this seat would rather ship
that than a generator racing GitHub to the bottom.

## 3. Product definition

Four commands in version 1.

- generate reads a project's artifacts and, where reachable, its live
  surface, and writes the dual path catalog plus a baseline file.
- validate checks a catalog file on its own, beyond schema. URN
  anchoring to the publisher domain, exactly one of url or data per
  entry, representative query counts, trust manifest shape, and dual
  path coherence.
- check is the drift gate. It compares published catalog, baseline and
  live surface and exits for CI. It runs in two modes. Repo mode is
  offline and compares the catalog against the repo's own artifacts.
  Live mode probes the deployed surface and compares all three sides.
- migrate is the adoption wedge, aimed at the 52 percent of measured
  publishers stranded on the legacy path. It ingests an existing
  ai-catalog.json, treats it as a claim to be verified rather than a
  truth to be copied, checks every entry against the live surface and
  the repo's artifacts, and emits the dual path pair plus a baseline
  and the CI gate wiring. Entries that verify carry over. Entries
  that fail verification are reported, never silently carried and
  never silently dropped. Section 5 sets out how this reaches the
  stranded population.

Out of scope for version 1. Running a registry or a search endpoint.
Writing agents.txt files, covered in section 7. Signing trust
manifests with publisher keys, covered in section 10. Generating
representative queries with a language model. Queries are derived
from artifact text by fixed templates or taken from publisher config,
never invented by a model call inside a deterministic tool.

### First customer, designed against dusk.fm's real surfaces

The reference output is dusk.fm's catalog, and dusk.fm's architecture
is on record from David's September 2026 provider survey. One remote
MCP server over Streamable HTTP with OAuth 2.0, built once and
consumed natively by ChatGPT, Claude, the Gemini tooling and
Copilot Studio, with thin per platform adapters carrying OAuth
client registrations, manifests and listing assets. Dawn, the
agent first booking and discovery layer over dusk.fm, is being
submitted as an official Muse connector on that foundation. Those
facts impose four design requirements that a hypothetical local
server would never have surfaced.

- The probe speaks Streamable HTTP as a first class transport, not
  only stdio. dusk.fm's production surface is a remote HTTP server.
  A stdio only checker would be blind to the first customer's real
  deployment and useful only in development repos.
- The server card is the primary declared evidence for dusk.fm,
  because its live surface answers an unauthenticated handshake with
  an authorization challenge. For authenticated publishers the check
  runs card against catalog against baseline, and the report labels
  the run as declared evidence only. It never prints the words live
  pass for a surface it could not touch. This is Amendment B carrying
  real weight, not tidiness.
- OAuth discovery metadata is itself a checked surface. The
  authorization server metadata and protected resource metadata a
  remote MCP server publishes are artifacts with bytes and hashes,
  so an authentication change, already a major drift class in
  section 6, is measured against them concretely rather than inferred
  from a failed handshake.
- The dusk.fm catalog itself is small and sharp. One MCP entry for
  the remote server, referenced by url to its server card and digest
  bound, with representative queries drawn from the booking and
  discovery actions the server actually serves. No API entry is
  invented for a REST surface the catalog has no evidence for, under
  Rule 1. The per platform listing manifests in the adapters are
  those platforms' own formats and stay out of this tool. almanac
  covers the ARD and server card layer that sits underneath all of
  them, which is exactly the layer no platform maintains for a
  publisher.

The cheapest failure test in section 9 runs against telorama, a
stdio server already shipping in the fleet, because it is the MCP
surface on hand in this workspace. That exercises generation, the
baseline and every drift class over stdio. It does not exercise the
Streamable HTTP transport or the authenticated degradation path, and
this record names that gap rather than letting the telorama result
stand in for it. The HTTP probe and the dusk.fm catalog are the
first build milestone after creation, in that order.

## 4. Generation inputs and their precedence

Inputs, in the order a publisher meets them.

- A live surface probe. For an MCP server, an initialize handshake
  plus tools/list, resources/list and prompts/list where offered. For
  a REST API, the OpenAPI document the deployment actually serves.
- An MCP server card, repo local or hosted at the locations the
  SEP-2127 extension defines, the endpoint's /server-card path
  first and the well known path behind it.
- An OpenAPI specification file in the repo.
- Skills directories. Each SKILL.md frontmatter block is read for name
  and description, and the file is hashed.
- A2A agent cards where a project ships them.
- agents.json and agents.txt blocks, read as corroboration only.
- Repo metadata such as README opening lines and package descriptions.
- A publisher config file, almanac.toml, holding editorial choices.

Precedence rules. The brief asks which artifact wins when the MCP card
and the OpenAPI spec disagree. The rules below answer that directly
and then cover the rest.

Rule 1. Existence is never editorial. No input may announce a
capability that the highest available evidence does not show. Config
may suppress an entry with a recorded reason. Config may never invent
one. A catalog that announces an unserved tool is the exact failure
this product exists to prevent.

Rule 2. For capability facts, live beats declared, and declared beats
inferred. The live probe wins on tool names, tool existence, endpoint
URLs and served version. Where no live probe is possible, for example
an authenticated server that answers 401 to an unauthenticated
handshake, the MCP server card wins for MCP facts and the OpenAPI
file wins for API facts. Repo metadata never wins a capability fact.

Rule 3. MCP card against OpenAPI, field by field. The two artifacts
describe different artifact kinds, so most fields never compete. Where
they do compete, the artifact that owns the entry kind wins. For an
MCP entry, the server card and the live probe own the transport, the
endpoint and the tool surface. For an API entry, the OpenAPI document
owns paths, operations and the servers URL. Shared fields are
publisher identity, display name and base domain. For shared fields
the order is live probe, then server card, then the OpenAPI info
block, then config. Every disagreement between the card and the spec
on a shared field is emitted as a generation warning naming both
values. Disagreements are surfaced, never silently resolved, because
a card and a spec that disagree are themselves a drift signal.

Rule 4. Editorial fields belong to the publisher. Display name
overrides, descriptions, tags and representative queries come from
config when present. Otherwise they derive in this order. Server card
description, OpenAPI info description, SKILL.md description for skill
entries, and only then repo metadata, with any entry built from repo
metadata flagged low confidence in the generation report.

Rule 5. Skills are file truth. A skill has no live surface. Its
SKILL.md frontmatter is authoritative for its entry and its content
hash is its baseline. If a skills directory and a server card both
claim the same skill, the file wins and the card claim is warned on.

Rule 6. agents.txt and agents.json never create entries. They can
corroborate an endpoint that another input already produced, and a
contradiction between them and the catalog is a drift class in
section 6. An announcement file is a claim, not evidence.

Provenance. Every generated entry records which input produced it and
which inputs were overruled, in a sidecar baseline file that is not
published. The published catalog stays spec clean. The baseline is
what check compares against, and it is committed to the publisher's
repo like a lockfile.

## 5. Dual path output contract

One internal model, two files, written in a single run.

- The current path is /.well-known/ard.json, carrying ARD v0.91
  entries and served as application/ard+json where the host allows
  the media type to be set.
- The legacy path is /.well-known/ai-catalog.json, carrying the same
  entries array and the same host block, byte identical in content.
- The two files are generated atomically from the same model. There
  is no mode that writes one without the other. A check run fails on
  path divergence, defined as any difference between the two entries
  arrays, so the pair cannot quietly split after generation.
- The server card, when the project has an MCP server, lives at two
  locations with identical content. The normative location is the
  one SEP-2127 Final defines, the endpoint's own path with
  /server-card appended, <endpoint>/server-card. The legacy
  location is /.well-known/mcp/server-card.json, which the Final
  text no longer names but major scanners still request, so a
  publisher dropping it would vanish from tools that work today.
  The tool writes the normative copy into the site when the
  endpoint lives on the site's own origin. A stdio server has no
  endpoint to append to, and an endpoint hosted on another origin
  keeps its normative copy with the server's operator, so those
  sites carry the well known copy alone and say so in the run's
  output.
  The catalog entry references the card by url at the well known
  path, because that path exists for every transport, including
  stdio servers that have no endpoint URL to append to. Both
  copies carry the same bytes, the entry's one digest binds both,
  and the baseline records both as artifacts of the entry, so a
  copy that diverges or disappears is drift like any other
  announced artifact.
- Canonical form. Keys sorted, two space indent, LF line endings, one
  trailing newline. Same inputs produce the same bytes. This is what
  makes a catalog reviewable in a pull request diff.
- Digest binding. Every entry that references an artifact by url
  carries the digest field the ARD draft defines, a sha256 digest of
  the referenced artifact as served. A referenced card or skill file
  that changes without the catalog changing is then detectable from
  the catalog alone, without the baseline, which is what lets a
  third party spot a tampered or stale descriptor. The prototype in
  section 9 generates these digests and the drift checker verifies
  them.
- Sunset rule. The legacy file is dropped only when both reader
  populations have moved, meaning the ARD spec no longer names the
  predecessor path and the MCP card extension names ard.json. Until
  then the pair ships. The tool warns about the legacy path's status
  and never removes it on its own.

Why both paths, in evidence. 52 percent of 527 measured publishers
still serve only the legacy path, a conformant ARD registry is not
required to read that path, and MCP card readers are not required to
read the new one. Dual path is the only posture that reaches both
populations, and keeping the pair coherent is work no browser
generator does.

The migration service, and how it reaches the stranded. The 274 or
so stranded publishers are not an abstraction. They are enumerable,
because registries crawl the well known paths and the legacy only
population is visible in that crawl data. Reaching them works like
this. The migrate command needs no config file and no account. A
publisher runs one command in their repo, or adds the GitHub Action
and lets it open a pull request, and gets the verified dual path
pair, the baseline and the gate. The offer to a stranded publisher
is not learn a new standard. It is keep the file you already serve,
gain the file the registries now read, and get a CI check that the
pair never lies again. Migration is also where the drift gate earns
its first proof, because a legacy catalog that has sat untouched
since the path moved is the catalog most likely to announce tools
the server no longer serves, and migrate reports those on the first
run. The wedge and the product are the same motion. A publisher who
migrates has the baseline, and a publisher with a baseline is one
config line from the gate.

## 6. Drift model

Three sides. P is the published catalog as served or as committed.
B is the baseline recorded at generation time. L is the live surface
probed at check time. Drift is any divergence among the three that a
publisher would want to know about before an agent discovers it for
them.

Drift classes and default severities.

Critical, always fails.

- An announced entry whose URL is dead or whose server fails its
  handshake. The catalog promises what the server no longer serves.
- An announced MCP tool that the live server no longer serves, by
  name. Renames land here, because a rename is a removal plus an
  addition from a client's point of view.
- A capability the live server serves that the catalog never
  announced. A new tool, a new OpenAPI operation, a new skill file.
- Dual path divergence between ard.json and ai-catalog.json.
- An entry whose URN is not anchored to the publisher domain. Scope
  note, read in the ARD Internet Draft for this record. A manifest
  may in principle carry entries from several publishers, and the
  draft is explicit that the manifest host, the URN publisher and
  the entry url host need not be the same domain. almanac version
  1 generates single publisher catalogs, so the rule applies to
  every entry it generates or baselines. Catalogs authored elsewhere
  are validated under their own publisher declarations, not under
  this rule.
- An entry carrying both url and data, or neither.
- A referenced artifact whose served bytes no longer match the
  digest recorded in its entry.

Major, fails by default and can be lowered by config.

- A tool whose input schema hash changed since baseline.
- A skill whose SKILL.md content hash changed since baseline without
  regeneration.
- An OpenAPI operation removed or renamed, or a new required
  parameter on an existing operation.
- A server version change since baseline.
- An authentication change, for example a surface that was open and
  now demands OAuth, or the reverse.
- A resource set change on the MCP surface, such as the view resource
  an MCP Apps host depends on disappearing.
- A prompt set change on the MCP surface. Added 2026-11-21 at the
  milestone one checkpoint, recorded here because section 6 presents
  its list as fixed. Prompts are part of the surface the probe
  records, and the class rides the same footing as the resource set
  change above.
- A catalog served only on the legacy path, with no ard.json beside
  it. The publisher is invisible to conformant ARD registries, which
  is the stranded state the migrate command exists to end. This
  class is what makes check useful to a publisher who has not
  migrated yet, before any other drift exists.

Minor, warns by default.

- A tool description changed since baseline.
- Display text, tags or ordering changes in a declared artifact.
- The catalog served with a generic JSON media type rather than
  application/ard+json. Most publishers get this wrong today, so it
  starts as a warning with a plan to promote it once the registry
  data shows the ecosystem moving.
- A trust manifest approaching its expiry date.

Not drift. Latency, response size, cache headers, and any change
inside a tool's behaviour that leaves its name, schema and
description untouched. Section 9 records this limit honestly. The
gate checks the announced contract, not the implementation behind it.

CI failure semantics.

- Exit 0 means no finding at or above the configured fail severity.
- Exit 1 means drift at or above the fail severity. The default fail
  severity is major.
- Exit 2 means the check itself could not complete, for example an
  unparseable catalog or a missing baseline. An announced server that
  is unreachable is not exit 2. It is a critical finding and exit 1,
  because unreachable is exactly what the catalog must not promise.
- The report is deterministic. Findings are sorted by severity, class
  and entry, and the same three sides produce the same report bytes
  apart from one isolated checked-at timestamp field.
- Suppressions live in almanac.toml, each with a reason and an
  expiry date. An expired suppression fails the check. Borrowed from
  the OKF stale_after discipline, a suppression that never expires is
  a lie waiting to happen.
- Repo mode runs on every pull request with no network. Live mode
  runs on a schedule and before releases, because live surfaces move
  when no pull request is open. Both modes are the same code path
  with a different surface source.

## 7. Relationship to agents.txt

agents.txt is a neighbouring spec, not a rival and not a duplicate.
The seat read its spec repository and its IETF draft for this record.

What agents.txt is. Two files at a site root, /agents.txt and its
structured companion /agents.json. They state which protocols a site
supports, covering payments, authorization, MCP servers, skill
packages and A2A agent cards. Its own framing is a capability
declaration layer above robots.txt, sitemap.xml and llms.txt. Its
reference generator is called herald, distributed on npm, and it
emits agents.txt, agents.json, robots.txt, llms.txt and sitemap.xml
from one hand maintained config file. The spec is CC0, the code is
Apache 2.0, and a June 2026 IETF draft asks for the two well known
URI registrations.

Where the two formats differ, in the ways that matter.

- Audience. agents.txt is read by an agent that has already arrived
  at the site. It is the notice on the door. ARD is read by
  registries that crawl publishers and answer searches from agents
  that have not found the site yet. It is the listing in the
  directory. A publisher needs the listing to be found and the
  notice to be used, and neither file does the other's job.
- Shape. agents.txt declares protocol support by kind, with the how
  left to each protocol's own layer, in its spec's own words the
  announcement, never the duplicate. ARD entries carry per resource
  identity, a domain anchored URN, representative queries for search
  ranking, capabilities for filtering, and an optional trust
  manifest. ARD is built for a search index. agents.txt is built for
  a single fetch.
- Source of truth. herald generates from a config a person maintains.
  almanac generates from the artifacts and the live surface, and
  then checks them. The upkeep model is opposite.

What almanac does about agents.txt in version 1.

- It reads agents.json blocks as corroborating input under Rule 6.
- It cross checks. If agents.json names an MCP endpoint that the ARD
  catalog does not announce, or the reverse, that is a minor finding
  in repo mode, because two public claims about one surface should
  not disagree.
- It can emit a short pointer snippet for a publisher to add to
  agents.json referencing their ard.json, which the agents.txt spec
  explicitly invites when it says to publish extra discovery files
  and reference them. almanac does not write or own the
  agents.txt files themselves. herald's seat is generation of that
  format, and this product does not duplicate a neighbour's working
  tool.
- If a later version generates agents.txt, that decision gets its
  own gate. It is not smuggled into version 1.

## 8. Stack proposal

Rust, the fleet default, with no exception requested.

- One workspace with two crates. A core library holding the catalog
  model, the generation rules, the baseline format and the drift
  logic, kept free of network and filesystem code so every rule is
  testable as a pure function. A CLI crate holding argument parsing,
  file access and the surface probes.
- The probe client is blocking HTTP and stdio JSON-RPC, with no async
  runtime. A checker that runs in CI should be small, start fast and
  behave identically everywhere. Dependencies stay at the fleet norm,
  serde and serde_json for data, a small HTTP client for probes, and
  nothing else without a written reason in the repo.
- Determinism is a design constraint, not a hope. Canonical JSON
  output, sorted collections everywhere, no wall clock inside the
  core, and hashes over canonical bytes for schemas, cards and skill
  files. Where trust manifest verification arrives later, RFC 8785
  canonicalisation is the known requirement and the fleet already
  carries that experience in verirun.
- Distribution. The binary is named almanac and the crates are
  almanac-core and almanac-cli, the bare crate name belonging to a
  dormant calendar tool, as section 1 records. The crates publish to
  crates.io, with GitHub releases carrying prebuilt binaries and a
  composite GitHub Action that installs the released binary and runs
  check. No npm or PyPI package in version 1, which is why the npm
  tombstone in section 1 does not block.
- The Python prototype in this phase is throwaway test scaffolding.
  It is not shipped, not ported and not a second implementation.

## 10. Scope amendments flagged to Main

These were proposals when written. Main ruled on 2026-11-20, and all
five are APPROVED. The rulings are recorded at the end of this
section and bind the build.

- Amendment A. Invert the headline. Present the product as a drift
  gate first and a generator second, in the README and the repo
  description. Reason, the counter case in section 2. Generation is
  the onboarding, checking is the retention.
- Amendment B. Treat the MCP server card as a first class artifact.
  Generate it where missing, reference it from the catalog, and hash
  it into the baseline. Reason, SEP-2127 makes the card a live
  reader surface, not an optional extra.
- Amendment C. Add the agents.json cross check as a version 1 drift
  class at minor severity. Reason, section 7. Two public claims
  about one surface disagreeing is cheap to catch and embarrassing
  to ship.
- Amendment D. Defer trust manifest signing. Version 1 validates
  trust manifest shape and expiry only. It does not generate JWS
  signatures or manage publisher keys. Reason, key management is a
  second product hiding inside the first, and a badly signed
  manifest is worse than an unsigned one. Validation keeps the
  drift promise without the key risk.
- Amendment E. Representative queries are templated or configured,
  never model generated, in version 1. Reason, determinism. The same
  repo must produce the same catalog on every machine, and a model
  call breaks that and adds a paid dependency to a CI gate.

Rulings, Main, 2026-11-20. A is approved, the headline inverts, drift
gate first and generator second, in the README and the repo
description. B is approved, the server card is a first class
artifact, generated where missing, referenced from the catalog,
hashed into the baseline. C is approved, the agents.json cross check
joins version 1 as a minor drift class, read and cross checked, never
generated in version 1. D is approved, trust manifest signing is
deferred, version 1 validates shape and expiry only, with no JWS and
no key management. E is approved, representative queries are
templated or configured and never model generated, and determinism
binds in full. Main also accepted the test's stated limits as stated.
The source level rename with a rebuild is owed as the stronger
version of the planted break, and the Streamable HTTP transport with
the authenticated degradation path stands as the first build
milestone after creation.

## 11. Risks and open questions

- ARD is still a proposal at v0.91. The spec may move fields before
  it settles. Mitigation, the catalog model is one module with the
  spec version pinned in one place, and the baseline records the
  spec version it was generated against.
- Authenticated surfaces limit the live probe. A server behind OAuth
  may expose nothing to an unauthenticated handshake beyond the fact
  of the 401. The check then degrades to card against catalog, and
  the report must say so rather than claim a live pass. This is the
  known weak leg and dusk.fm, an authenticated service, will hit it
  first. A credential aware probe, using a publisher supplied token
  from the CI secret store, is the planned answer and is flagged as
  the first post launch enhancement.
- Skill entry media typing is not settled in the ecosystem. This
  record uses text/markdown for a SKILL.md artifact and flags it as
  an open question to confirm against the ARD registry's practice
  before the first real publish.
- Registry behaviour is outside the gate. almanac can prove a
  catalog is accurate. It cannot prove a registry indexed it. A
  registry presence check is a possible later addition, kept out of
  version 1 so the gate's promise stays provable.
